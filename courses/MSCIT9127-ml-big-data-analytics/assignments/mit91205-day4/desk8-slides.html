Scenario 5 — Graph analytics

Graph analytics studies relationships. People or accounts are nodes. A call, a follow, or a transfer is an edge.

How Spark helps

  • GraphX, or GraphFrames, runs the graph across the cluster.
  • The graph is built from tables Spark already read.
  • PageRank marks important nodes. Connected components find communities.
  • Spark SQL joins those scores back onto the account table.

Where it is used

  • Social networks, telecom call graphs, and fraud rings in banking.

A bank can see which accounts keep paying each other. One account with millions of links slows a single task. That is skew, and the number of iterations decides the runtime.

Scenario 6 — Large-scale aggregation and reporting

Aggregation turns a huge table into the totals a manager can read: sums, counts, and averages by region, branch, or date.

How Spark helps

  • Spark SQL groups millions of rows on many machines.
  • A date partition means the job opens one day, not the whole history.
  • The result is a small Parquet or ORC table for the dashboard.

A bank can ask

  • Daily transaction totals, the busiest branches, monthly revenue, and a customer summary.

The heavy work runs once. The dashboard reads the summary, not the raw terabytes. Too many output files make the next read slow, so the write is coalesced first.

Batch processing and streaming

Reads data that is already stored.Reads events as they arrive.
Works on history: a day, a month, a year.Works at low delay, for alerts.
Example: monthly transaction totals.Example: a transfer that should be flagged now.

Tools named in the lecture

  • Batch on this day: Apache Spark.
  • Streaming, which is Day 5: Spark Structured Streaming, Apache Kafka, and Apache Flink.

Both can use a DataFrame, so the code looks similar. The execution does not. Batch can rerun from files. A stream has to keep up, and it has to decide whether time means when the event happened or when the job saw it.

What Spark does not do for you

  • Memory: a cache of a large table needs RAM on the executors.
  • Shuffle: a join or a group moves rows between machines, and that move is the costly part.
  • Skew: one key with far too many rows makes one task last much longer than the others.
  • Cost: a cluster needs machines, memory, and storage.
  • Storage: Spark reads and writes. HDFS, Hive, or Parquet holds the bytes.
  • Tuning: partition count, memory, and the join strategy change the runtime.

Spark is the engine. The files live somewhere else. A good result still depends on the layout of those files and on a plan that avoids an unnecessary shuffle.

Close

Spark is a distributed engine for data that is too large for one machine.

  • Graph analytics, from tables of people and links.
  • Aggregation and reporting, from raw transactions to a small summary.
  • Machine learning, through MLlib, when the training set itself is large.
  • Batch today. Streaming is the same family of tools, and it is Day 5.

Spark turns raw files into information a decision can use. It does that by reading storage, computing, and writing the result back.
